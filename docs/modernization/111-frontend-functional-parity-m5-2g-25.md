## 1. Executive decision

The Next.js storefront now has meaningful disposable browser coverage for the
canonical Fastify workflows. The final Playwright run passed 11/11 scenarios,
including catalog browsing, search and architecture filtering, local auth and
CSRF, OIDC/SAML synthetic callbacks, WSS, statistics, scores, metrics, token
management, publishing, approval, rejection, administration and legacy deep
links. The new tests use a disposable SQLite database, immutable object root,
Fastify process, Next.js process and synthetic HTTPS dual-origin edge.

The application result remains `FRONTEND_FUNCTIONAL_PARITY_PARTIAL`, not GO.
Registration completion, password-management/reset UI, durable draft editing,
review notes, and a dedicated rejected-submission resubmission action remain
unimplemented or not browser-verified. The tested publisher flow can submit a
new bundle through the existing “Submit another” entry point, but the backend
does not expose a separate rejected-submission edit/resubmit contract.

No operational routing, Authentik resource, database, object store, Docker
service or sibling repository was modified.

Evidence: `BROWSER_VERIFIED`, `UNIT_VERIFIED`, `DOCKER_VERIFIED`,
`OPERATIONAL_CUTOVER_NO_GO`.

## 4. Required-equivalent capabilities

The critical path is complete in the disposable target:

- Anonymous catalog, detail, media, download, scores, statistics, profiles,
  docs and PWA assets.
- Search, architecture filtering and protected-route denial.
- Local login/logout, session continuity, CSRF boundary and current-user UI.
- API token creation, listing and rename; revoke remains covered by backend
  contract tests.
- Publisher submission through canonical Fastify and ownership-scoped workspace.
- Reviewer approval publishes the cartridge and makes it visible/downloadable.
- Reviewer rejection persists `rejected` and exposes that state to the owner.
- Administrator read surfaces and generic federation provider administration.

The following are not yet complete enough for a parity GO:

- Registration email delivery and one-time completion in a browser.
- Password change/reset UI and end-to-end recovery.
- Durable client-side draft persistence before bundle submission.
- Review notes as a user-visible workflow; the current canonical contract
  supports editable approval metadata but not a dedicated notes field.
- Dedicated rejected-submission edit/resubmit action. A new submission can be
  started, but the previous rejected record is not edited in place.
- Browser verification of every administrative mutation, backup/restore UI,
  and multi-page pagination using a dataset larger than the disposable fixture.

Evidence: `BROWSER_VERIFIED`, `UNIT_VERIFIED`, `NOT_VERIFIED`.

## 5. Compatibility redirects and intentionally retired behavior

Verified compatibility behavior includes:

- `/auth/login?return_to=...` redirects to the Next login page while preserving
  the safe return path.
- Native Next pages own `/games/[gameId]` and `/users/[username]` deep links.
- `/setup` remains a safe settings redirect; it does not expose deployment
  secrets or filesystem mutation.
- `/editor/submissions...` is redirected to the Next review workspace.
- `/auth/register`, `/auth/register/complete` and `/auth/tokens` remain
  compatibility namespaces owned by the modern auth UI/API boundary.

Intentionally retired from the public Next workflow:

1. Flask deployment/setup mutation. Deployment infrastructure is not a safe
   public application capability; application settings use the protected admin
   workspace instead.
2. Server-rendered Flask editor forms as the primary review UI. Their safe
   compatibility path is the Next review workspace; Fastify remains the
   authorization and publication authority.

These are compatibility decisions, not authorization to delete Flask or its
templates.

Evidence: `SOURCE_VERIFIED`, `BROWSER_VERIFIED`.

## 7. Implemented frontend changes

### 7.1 Browser harness reliability

- Next E2E processes now use Webpack dev mode to avoid disposable Turbopack
  React Client Manifest races under repeated isolated runs.
- Every run receives an isolated validated `PRG32_NEXT_DIST_DIR` such as
  `.next-m52g14-<pid>-<port>`; cleanup removes only that exact directory.
- Global setup now cleans child processes, edge/provider servers and temporary
  roots when setup fails, preventing orphaned servers and stale Next locks.
- Startup probes wait for storefront HTML, login, catalog, auth providers and
  API health before browser execution.
- The disposable auth rate limit is explicitly 20 attempts per minute only in
  the Playwright backend fixture so 11 sequential workflows do not collide.

### 7.2 Functional ownership and contracts

- Removed the `/users/:path*` legacy rewrite from `frontend/next.config.ts`.
  Next profile pages now own `/users/[username]` and `/users/[username]/runs`;
  profile data continues through `/api/users/...`.
- Added canonical auth token, registration and profile contract types/schemas.
- Accepted the documented legacy numeric submission identifier and canonical
  storage-v2 string cartridge identifier in the workflow result schema without
  weakening other identifier validation.
- Added `frontend/e2e/m52g25.spec.mjs` with six new browser workflows.
