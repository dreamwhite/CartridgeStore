PRG32 CARTRIDGE STORE - ROUTE E RESPONSE REFERENCE
==================================================

Documento ricavato dal codice del repository.
Ultimo controllo: 2026-07-23.

SCOPO
-----

Questo file descrive tutte le route HTTP e WebSocket definite
dall'applicazione, incluse:

- pagine HTML pubbliche;
- autenticazione locale e federata;
- amministrazione;
- catalogo e pubblicazione cartridge;
- revisione editoriale;
- leaderboard;
- metriche;
- statistiche;
- profili utente;
- multiplayer WebSocket;
- discovery mDNS/PWA.

Gli esempi mostrano la "response shape", non valori garantiti.
I timestamp possono essere:

- ISO 8601 UTC, per esempio "2026-07-23T15:30:00Z";
- datetime SQLite, per esempio "2026-07-23 15:30:00";
- Unix timestamp in secondi;
- timestamp in millisecondi, per le run firmware.


CONVENZIONI GENERALI
====================

Base URL locale:

    http://127.0.0.1:5080

Tipi di autenticazione supportati:

1. Sessione Flask

   Creata da POST /auth/login e inviata automaticamente dal browser
   attraverso il cookie di sessione.

2. Bearer token

   Header:

       Authorization: Bearer prg32_xxxxxxxxx

3. Token legacy PRG32_USERS

   Accettato tramite:

       Authorization: Bearer <token>

   oppure:

       X-PRG32-Token: <token>

   Alcune route leggono anche:

       ?token=<token>

4. Login OIDC o SAML

   Disponibile soltanto quando il relativo adapter viene abilitato
   all'avvio.


RUOLI E GRUPPI
--------------

Ruoli:

    reader     livello 0
    user       livello 1
    player     livello 1
    publisher  livello 2
    admin      livello 3

Gruppo speciale:

    editors

Nota importante:

- molte route di scrittura usano login_required, non un ruolo specifico;
- le route di revisione richiedono il gruppo editors;
- le route amministrative richiedono admin;
- le route cartridge admin accettano admin oppure editors.


PRINCIPAL / USER SHAPE
----------------------

Le route /api/me e /auth/me usano questa struttura:

    {
      "id": 1,
      "name": "admin",
      "username": "admin",
      "email": "admin@localhost",
      "role": "admin",
      "groups": ["editors"],
      "authenticated": true
    }

Utente anonimo:

    {
      "id": null,
      "name": "anonymous",
      "username": "anonymous",
      "email": "",
      "role": "reader",
      "groups": [],
      "authenticated": false
    }


ERRORI DI AUTENTICAZIONE JSON
-----------------------------

401, utente non autenticato:

    {
      "ok": false,
      "error": "login required",
      "user": {
        "id": null,
        "name": "anonymous",
        "username": "anonymous",
        "email": "",
        "role": "reader",
        "groups": [],
        "authenticated": false
      }
    }

403, permesso insufficiente:

    {
      "ok": false,
      "error": "admin role required",
      "user": { ...Principal }
    }

Per richieste HTML:

- un 401 normalmente produce un redirect 302 verso /auth/login;
- un 403 normalmente renderizza templates/error.html.


ERRORI APPLICATIVI JSON
-----------------------

StoreError, errori cartridge e validazione metadata:

    HTTP 400
    {
      "ok": false,
      "error": "descrizione dell'errore"
    }

Upload troppo grande:

    HTTP 413
    {
      "ok": false,
      "error": "upload is too large"
    }

Nota: alcune risorse catalogo mancanti generano attualmente 400 attraverso
StoreError, non 404.

1. PAGINE PUBBLICHE E PWA
=========================

GET /
-----

Scopo:

    Catalogo HTML delle cartridge.

Auth:

    Pubblica.

Query:

    q             ricerca su id, titolo, summary, tag e autori
    page          pagina, minimo 1; default 1
    per_page      elementi per pagina; default 24; massimo 100
    limit         alias di per_page

Successo:

    HTTP 200
    Content-Type: text/html
    Template: templates/index.html

La pagina contiene:

- griglia delle cartridge;
- ricerca;
- paginazione;
- titolo, summary, versione, architetture e tag.


GET /games/<game_id>
--------------------

Scopo:

    Pagina HTML di dettaglio cartridge.

Auth:

    Pubblica.

Path:

    game_id        ID cartridge

Query:

    version        versione selezionata; altrimenti latest_version

Successo:

    HTTP 200
    Content-Type: text/html
    Template: templates/game.html

Contenuto:

- icona e screenshot;
- metadata;
- versioni;
- download per architettura;
- autori;
- leaderboard;
- numero download;
- colophon.

Errori:

    HTTP 400 se gioco o versione non esistono.


GET /scores
-----------

Scopo:

    Leaderboard HTML.

Auth:

    Pubblica.

Query:

    player         filtro esatto player
    limit          1..100, default 50

Successo:

    HTTP 200
    Content-Type: text/html
    Template: templates/scores.html


GET /stats

Scopo:

    Dashboard HTML delle statistiche.

Auth:

    Pubblica.

Query:

Successo:

    HTTP 200

    Template: templates/stats.html

Contenuto:

- totale download;
- trend SVG;
- giochi più scaricati;
- download per architettura;
- run attive negli ultimi sette giorni.

2. AUTH LOCALE E TOKEN
======================

GET /auth/register
------------------

Scopo:

    Form HTML per richiedere la registrazione via email.

Auth:

    Pubblica.

Successo:

    HTTP 200
    Content-Type: text/html
    Template: templates/auth_register.html


POST /auth/register
-------------------

Scopo:

    Crea e invia un link di completamento registrazione.

Auth:

    Pubblica.

Content-Type:

    application/x-www-form-urlencoded

Form:

    email           obbligatoria, formato email valido

Comportamento:

- controlla auth_allow_registration;
- può limitare il dominio tramite auth_require_email_domain;
- il token scade dopo 24 ore;
- se SMTP non è configurato il link viene scritto nei log;
- la risposta non rivela se un account esiste già.

Successo HTML:

    HTTP 200
    Template: templates/auth_register_sent.html

Successo JSON:

    Richiedere Accept: application/json.

    HTTP 200
    {
      "ok": true,
      "email": "student@example.edu",
      "message": "registration email sent"
    }

Errori JSON:

    HTTP 400
    {
      "ok": false,
      "error": "email must be valid"
    }

Altri errori possibili:

    registration is closed
    email must belong to example.edu


GET /auth/register/complete
---------------------------

Scopo:

    Form HTML aperto dal link ricevuto via email.

Auth:

    Pubblica.

Query:

    token           token di registrazione obbligatorio

Successo:

    HTTP 200
    Template: templates/auth_register_complete.html

Errori:

    HTTP 400, pagina HTML di errore, se token assente, scaduto o usato.


POST /auth/register/complete
----------------------------

Scopo:

    Completa la registrazione e apre la sessione.

Auth:

    Pubblica, ma richiede un token registrazione valido.

Content-Type:

    application/x-www-form-urlencoded

Form:

    token               obbligatorio
    password            minimo 10 caratteri
    password_confirm    deve coincidere

Successo HTML:

    HTTP 302 verso next oppure /
    Imposta il cookie di sessione.

Successo JSON:

    Usare Accept: application/json.

    HTTP 200
    {
      "ok": true,
      "user": { ...Principal }
    }

Errori:

    HTTP 400
    {
      "ok": false,
      "error": "registration link is invalid or expired"
    }

    HTTP 400
    {
      "ok": false,
      "error": "password must be at least 10 characters; password confirmation does not match"
    }

    HTTP 400
    {
      "ok": false,
      "error": "account already exists"
    }

Nota:

    Anche in modalità JSON i dati vengono attualmente letti da request.form,
    non da un body JSON.


GET /auth/login
---------------

Scopo:

    Form HTML di login.

Auth:

    Pubblica.

Query:

    next            percorso locale di redirect dopo il login

Successo:

    HTTP 200
    Template: templates/auth_login.html


POST /auth/login
----------------

Scopo:

    Login locale tramite username/email e password.

Auth:

    Pubblica.

Content-Type:

    application/x-www-form-urlencoded

Form:

    username        username oppure email
    password
    next            redirect locale opzionale

Successo HTML:

    HTTP 302 verso next oppure /
    Imposta il cookie di sessione.

Successo JSON:

    Usare Accept: application/json.

    HTTP 200
    {
      "ok": true,
      "user": { ...Principal }
    }

Credenziali errate:

    HTTP 401
    {
      "ok": false,
      "error": "invalid username or password"
    }

Nota:

    Anche in modalità JSON le credenziali vengono lette da request.form.


POST /auth/logout
-----------------

Scopo:

    Cancella la sessione corrente.

Auth:

    Login richiesto.

Successo HTML:

    HTTP 302 verso /

Successo JSON:

    Con Accept: application/json oppure body JSON:

    HTTP 200
    {
      "ok": true
    }

Errori:

    HTTP 401 se non autenticato.


GET /auth/me
------------

Scopo:

    Restituisce l'utente corrente, ma richiede login.

Auth:

    Login o Bearer token.

Successo:

    HTTP 200
    {
      "ok": true,
      "user": { ...Principal }
    }

Errori:

    HTTP 401 se anonimo.


POST /auth/tokens
-----------------

Scopo:

    Crea un nuovo Bearer token per l'utente corrente.

Auth:

    Login richiesto.

Body JSON:

    {
      "label": "board ESP32-C6"
    }

In alternativa form:

    label=board ESP32-C6

Il label viene troncato a 80 caratteri e assume "API token" come default.

Successo:

    HTTP 200
    {
      "ok": true,
      "id": 12,
      "label": "board ESP32-C6",
      "token": "prg32_xxxxxxxxxxxxxxxxxxxxxxxxx"
    }

Nota:

    Il token in chiaro viene mostrato soltanto in questa response.


DELETE /auth/tokens/<int:token_id>
----------------------------------

Scopo:

    Revoca un token appartenente all'utente corrente.

Auth:

    Login richiesto.

Path:

    token_id        ID numerico del token

Successo:

    HTTP 200
    {
      "ok": true
    }

Token inesistente o appartenente a un altro utente:

    HTTP 200
    {
      "ok": false
    }


3. AUTH FEDERATA OPZIONALE
==========================

Queste route vengono registrate soltanto quando il provider è abilitato e
configurato correttamente all'avvio dell'applicazione.


GET /auth/oidc/login
--------------------

Scopo:

    Avvia il login OpenID Connect.

Disponibilità:

    Richiede OIDC enabled, issuer, client ID, client secret e authlib.

Successo:

    HTTP 302 verso l'authorization endpoint dell'Identity Provider.


GET /auth/oidc/callback
-----------------------

Scopo:

    Callback OIDC.

Query:

    Parametri OAuth/OIDC forniti dall'Identity Provider.

Successo:

- crea o aggiorna l'utente locale;
- imposta la sessione;
- aggiorna last_login;
- HTTP 302 verso /.

Errori:

    Errori del provider o profilo privo di sub/email possono produrre 500.


GET /auth/saml/login
--------------------

Scopo:

    Avvia il login SAML 2.0.

Disponibilità:

    Richiede configurazione IdP completa e python3-saml.

Successo:

    HTTP 302 verso l'Identity Provider.


POST /auth/saml/acs
-------------------

Scopo:

    Assertion Consumer Service SAML.

Body:

    Form SAMLResponse e parametri SAML.

Successo:

- crea o aggiorna l'utente locale;
- imposta la sessione;
- aggiorna last_login;
- HTTP 302 verso /.

Errore autenticazione:

    HTTP 401
    Content-Type: text/plain
    SAML authentication failed.


GET /auth/saml/metadata
-----------------------

Scopo:

    Metadata XML del Service Provider.

Successo:

    HTTP 200
    Content-Type: application/xml
    Body: XML metadata SAML.

Errore validazione metadata:

    HTTP 500
    Content-Type: text/plain


LDAP
----

Il modulo LDAP non registra route. Se PRG32_LDAP_URL è presente, controlla
soltanto la disponibilità di ldap3 e scrive un warning: il login LDAP
interattivo non è implementato in questa build.


4. CATALOGO E DISCOVERY API
===========================

GET /.well-known/prg32-store.json
---------------------------------

Scopo:

    Discovery document ufficiale per firmware e tool PRG32.

Auth:

    Pubblica.

Successo:

    HTTP 200
    {
      "abi": "prg32-store-discovery-1.0",
      "name": "PRG32 Cartridge Store",
      "api": "http://host:5080/api",
      "web": "http://host:5080/",
      "version": "1.0.0",
      "auth_enabled": true,
      "roles": ["reader", "user", "player", "publisher", "admin"],
      "services": {
        "cartridges": "http://host:5080/api/games",
        "bundle_publish": "http://host:5080/api/publish/bundle",
        "submissions": "http://host:5080/api/submissions",
        "scores": "http://host:5080/api/scores",
        "metrics": "http://host:5080/api/runs",
        "multiplayer": "ws://host:5080/api/multiplayer",
        "multiplayer_status": "http://host:5080/api/multiplayer/status"
      }
    }

Note:

- con HTTPS multiplayer usa wss://;
- PRG32_STORE_PORT sostituisce la porta presente in request.host;
- i campi sono ABI pubblica e non devono essere rimossi.

GET /api/games
--------------

Scopo:

    Lista pubblica delle cartridge.

Auth:

    Pubblica.

        "has_next": true,
        "has_prev": false,
        "next_page": 2,

GET /api/games/<game_id>/download
---------------------------------

Scopo:

    Scarica un artefatto .prg32 e registra un download.

Auth:

    Pubblica.

Query:

    version
    architecture

Se architecture è assente:

- preferisce esp32c6;
- altrimenti sceglie la prima architettura ordinata.

Successo:

    HTTP 200
    Content-Type: application/vnd.prg32.cartridge
    Content-Disposition: attachment;
      filename="<id>-<version>-<architecture>.prg32"
    Body binario.

Effetto collaterale:

    Inserisce un download_event con game, versione, architettura,
    user_id opzionale, hash IP e User-Agent.

Errori:

    HTTP 400 se variante o file non esistono.


5. PUBBLICAZIONE
================

GET /publish
------------

Scopo:

    Pagina HTML di upload.

Auth:

    Login richiesto.

Query:

    token           riportato nel template, per compatibilità

Successo:

    HTTP 200
    Template: templates/publish.html

Anonimo:

    HTTP 302 verso /auth/login.


POST /publish
-------------

Scopo:

    Upload browser di un bundle ZIP.

Auth:

    Login richiesto.

Content-Type:

    multipart/form-data

Form:

    bundle          file .zip obbligatorio

Successo:

    HTTP 302 verso /publish
    Flash:
      Package uploaded for editor review as submission #<id>.

Errori:

    HTTP 400 pagina HTML.
    HTTP 413 per bundle troppo grande.


POST /api/publish/bundle
------------------------

Scopo:

    Endpoint JSON principale per pubblicare un package.

Auth:

    Login o Bearer token.

Content-Type:

    multipart/form-data

Form:

    bundle          ZIP obbligatorio

Struttura ZIP minima:

    manifest.json
    icon.png
    game-esp32c6.prg32

Manifest indicativo:

    {
      "abi": "prg32-metadata-1.0",
      "id": "org.example.game",
      "title": "Example Game",
      "version": "1.0.0",
      "authors": [{"name": "Ada"}],
      "assets": {
        "icon": "icon.png",
        "splash": "splash.png"
      },
      "architectures": [
        {"id": "esp32c6", "file": "game-esp32c6.prg32"},
        {"id": "qemu", "file": "game-qemu.prg32"}
      ],
      "colophon": { ... }
    }

          "architecture": "esp32c6",
          "file": "game-esp32c6.prg32"

          "architecture": "qemu",
          "file": "game-qemu.prg32"
        }
      ]
    }

Errori:

    HTTP 400
    {
      "ok": false,
      "error": "bundle must be a zip file"
    }

Altri errori possibili:

    missing upload: bundle
    empty upload: bundle
    bundle must be a valid zip file
    bundle is missing manifest.json
    manifest.abi must be prg32-metadata-1.0
    manifest.assets must be an object
    bundle icon file is missing
    bundle icon must be PNG or JPEG
    manifest.architectures must be a non-empty array
    duplicate architecture: esp32c6
    architecture.file must point to a .prg32 file
    bundle cartridge file is missing: <file>

Upload eccessivo:

    HTTP 413
    {
      "ok": false,
      "error": "bundle upload is too large"
    }

Campi obbligatori:

    board_id        max 40
    target          max 24

Campi opzionali:

    display_backend       max 24
    firmware_version      max 32
    firmware_git_sha      max 24
    game_name             max 40
    sample_period_frames  intero >= 1
    started_ms            intero >= 0; default ora

Conflitto run_id:

    Esegue un upsert e sostituisce i metadata della run.

Successo:

    HTTP 200
    {
      "ok": true,
      "run_id": "run-001"
    }

Input errato:

    HTTP 400
    {
      "ok": false,
      "error": "expected run_id, board_id, target"
    }


POST /api/metrics/batch
-----------------------

Scopo:

    Inserisce un batch di campioni.

Auth:

    Pubblica per compatibilità firmware.

Body JSON:

    {
      "run_id": "run-001",
      "dropped_samples": 0,
      "samples": [
        { ...Sample }
      ]
    }

Comportamento:

- campioni non-object vengono ignorati;
- numeri non validi diventano default numerici;
- valori numerici negativi diventano 0;
- UNIQUE(run_id, frame) evita duplicati;
- dropped_samples viene sommato se maggiore di zero.

Successo:

    HTTP 200
    {
      "ok": true,
      "inserted": 1,
      "received": 1
    }

Input errato:

    HTTP 400
    {
      "ok": false,
      "error": "expected run_id and samples"
    }

    HTTP 404
    {
      "ok": false,
      "error": "run_id not found"
    }

17. MULTIPLAYER WEBSOCKET
=========================

WS /api/multiplayer
-------------------

Connessione:

    ws://host:5080/api/multiplayer

Token opzionale:

    Authorization: Bearer <token>
    X-PRG32-Token: <token>
    ?token=<token>

L'autenticazione multiplayer è attiva soltanto se il relay è stato creato
con una lista PRG32_USERS non vuota. In quel caso serve un principal con
ruolo minimo player.


CLIENT -> SERVER: join
----------------------

    {
      "type": "join",
      "signature": "pong-v1",
      "flags": 1,
      "player_id": 123,
      "token": "opzionale"
    }

signature:

- obbligatoria;
- 1..47 caratteri;
- ammessi lettere, numeri, "_", ".", ":", "-".

player_id:

- opzionale;
- usato se > 0 e libero;
- altrimenti assegnato automaticamente.

SERVER -> CLIENT: welcome
-------------------------

    {
      "type": "welcome",
      "player_id": 123
    }

Dopo welcome, il nuovo peer riceve lo stato noto degli altri peer della
stessa signature.


CLIENT -> SERVER: state
-----------------------

    {
      "type": "state",
      "x": 120,
      "y": 80,
      "sprite": 0,
      "flags": 0,
      "input": 2,
      "frame": 42
    }

La state viene inoltrata agli altri peer nella stessa stanza.

Normalizzazioni:

    x, y        -32768..32767
    sprite      0..65535
    flags       0..65535
    input       0..4294967295
    frame       0..4294967295


SERVER -> CLIENT: peer
----------------------

    {
      "type": "peer",
      "player_id": 123,
      "x": 120,
      "y": 80,
      "sprite": 0,
      "flags": 0,
      "input": 2,
      "frame": 42
    }


CLIENT -> SERVER: leave
-----------------------

    {
      "type": "leave"
    }


SERVER -> CLIENT: leave
-----------------------

    {
      "type": "leave",
      "player_id": 123
    }

Inviato agli altri peer quando un giocatore lascia o si disconnette.


SERVER -> CLIENT: error
-----------------------

JSON non valido:

    {
      "type": "error",
      "error": "invalid json"
    }

Tipo sconosciuto:

    {
      "type": "error",
      "error": "unknown message type"
    }

State prima di join:

    {
      "type": "error",
      "error": "join first"
    }

Signature non valida:

    {
      "type": "error",
      "error": "invalid signature"
    }

Stanza piena:

    {
      "type": "error",
      "error": "game room is full"
    }

Permesso insufficiente:

    {
      "type": "error",
      "error": "player role required",
      "user": { ...Principal }
    }


18. STATUS CODE RIEPILOGATIVI
=============================

200

    Richiesta completata. Le API di delete possono comunque restituire
    {"ok": false} con status 200 se la risorsa non era eliminabile.

302

    Redirect delle route HTML dopo login, form o mutazioni.

400

    Input non valido, metadata/cartridge non validi, risorsa GameStore
    mancante oppure operazione incompatibile con lo stato corrente.

401

    Login richiesto o credenziali non valide.

403

    Utente autenticato ma senza ruolo/gruppo richiesto, oppure accesso a
    run altrui.

404

    Submission, run o pagina profilo non trovata. Le route GameStore
    usano generalmente 400.

413

    Upload oltre il limite.

500

    Eccezioni non gestite esplicitamente, per esempio alcuni conflitti
    SQLite UNIQUE o errori dei provider federati.
